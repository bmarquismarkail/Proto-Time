# Browser inspection and video-memory viewers

Build `time-browser`, then run `build-working/time-browser --core gameboy|gamegear --rom ROM`.
Game Boy is the compatibility default. The process prints its loopback URL, ROM digest and tested-source identity. Open that URL in a browser. `--port PORT` selects a port; zero chooses a free port. `--assets DIRECTORY` relocates the three bounded static assets (the default is `browser-assets` beside the executable).

The sole machine worker acquires a baseline debugger execution lease. It starts paused. Run, pause, instruction stepping, breakpoints, side-effect-free paused inspection and atomic RAM/register edits use the same generation/pause validation as the debugger. Incompatible capture, native mods, guest input plugins and other execution leases remain rejected by the core. Running guest input is neutral; deterministic remote input belongs to the separate frame-lockstep service. No ROM upload or host file browsing is exposed.

The machine worker captures a complete owned frame, video state and CPU reply every 16 ms while running. Paused state, edits, generations and command rejection counters publish immediately when they change; unchanged paused sessions retain their last owned snapshot. Three slots exchange ownership without a lock or allocation in the mailbox; overwritten samples are explicitly counted. A sample is an inspection snapshot, not a promise that one display frame retired. Palette expansion, pattern decoding, pixel provenance, JSON serialization, sockets, browser canvas and overlays run outside the machine lane. One bounded background decode runs independently of socket deadlines; the three-slot mailbox and one pending decode coalesce captures while it works, with explicit drop counts. CPU replies publish independently of video decoding. `videoSequence`, `videoCycles`, `videoGeneration` and `videoPauseId` bind every displayed video/resource view to its capture; the top-level sequence/cycles and CPU identify the latest owned CPU publication. Tooling must not treat these asynchronous observations as one coordinated checkpoint. The standalone worker uses bounded execution slices and host pacing; this is not a new core execution backend.

Game Boy inspection includes all 384 two-bit patterns, BGP/OBP registers, VRAM maps, the 40-entry OAM, canonical pixels and pixel-to-resource links. Game Gear inspection includes all 512 four-plane patterns, both CRAM palettes, eleven exposed VDP registers, actual VRAM sprite-table entries for all 64 sprites and pixel-to-resource links. The Game Gear compatibility OAM array is preserved separately; it is not substituted for the VDP sprite table. Sprite palette selection uses original pattern indices, including duplicate CRAM colors. Pattern/source addresses and observed resource metadata are presented as observations, not gameplay-purpose claims.

HTTP is restricted to numeric loopback, exact Host and same-origin requests. Mutations require the per-process random token. Eight nonblocking clients have 8 KiB headers, 4 KiB command bodies, 4 MiB responses and ten-second deadlines. Duplicate HTTP headers, transfer encodings, invalid identities, unsafe extents, unsupported operations and queue overflow are explicit rejections. Each accepted command has an exact reply ID; disconnecting before acknowledgment does not roll back an already committed guest edit. Reconnect and inspect the current generation before retrying. There is no authentication for use across untrusted networks, and the service does not bind external addresses.

`smoke-browser-inspector` checks both actual cores, owned snapshot independence, decoded extents, source metadata, malformed commands and concurrent mailbox accounting. `smoke-browser-cli` is an independent HTTP client checking both cores, real stepping, normal/unsupported/stale edits, views, overload, origin/host rejection, disconnection and shutdown. TSAN covers the handoff and real machine/transport workers. Browser layout, canvas/pixel interaction and controls require separate live evidence; GPU execution, physical presentation latency and audible/controller acceptance are not established by these headless tests.
